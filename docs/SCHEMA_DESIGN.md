# Diseño canónico del esquema

- **Estado:** propuesta para validación (Fase 0)
- **Alcance:** esquema PostgreSQL, reglas de validación y estrategia de migración
- **Fuera de alcance:** lógica de recomendación, embeddings definitivos, agente

## 1. Contexto

Hoy conviven dos esquemas (`01-create-schema.sql` y `01-create-schema-ENHANCED.sql`),
migraciones `V2`–`V5` que solo cubren `cards`, y entidades JPA que esperan columnas
que no existen (`formats`, `decks`). No hay nada desplegado ni datos que preservar,
así que se adopta un **`V1` único y consolidado**.

## 2. Principios

1. **Flyway es la única fuente de verdad.** No hay scripts de bootstrap en runtime.
2. **Una sola representación por concepto.** La legalidad vive en `card_legality`,
   no duplicada en `formats`.
3. **Reglas genéricas, sin hardcodear nombres de formato.** `max_copies` y
   `singleton` sustituyen los `IF format_name = 'Commander'`.
4. **Timestamps estándar:** `created_at` / `updated_at` en `TIMESTAMPTZ`.
5. **IDs `BIGINT` identity** en todas las tablas.
6. **Sin palabras reservadas** (`private`, `format`) como nombres de columna.
7. **La IA no decide legalidad.** El esquema y el servicio son deterministas.

## 3. Decisiones cerradas

| ID | Decisión |
|---|---|
| D1 | Un único `V1__baseline_schema.sql` consolidado; se eliminan `V2`–`V5` y los bootstrap |
| D2 | `formats` con reglas (`min/max_deck_size`, `max_sideboard_size`, `max_copies`, `singleton`, `requires_commander`); legalidad solo en `card_legality` |
| D3 | Validación en Java **y** trigger SQL (ADR-002) |
| D4 | Usuarios propios + BCrypt + JWT |
| D5 | `embedding` fuera de `V1`; se añade en `V3` cuando se decida modelo y dimensión |
| — | Renombres: `set_id`, `related_card_id`, `is_basic_land`, `is_private`, `format_id`; se elimina `decks.deck_type` |
| — | `created_at`/`updated_at` internos; la API mantiene `creation_date`, `last_modification` y `registration_date` |
| — | Formatos semilla: Standard, Commander, Modern, Legacy, Vintage y Pauper (sin Draft ni Brawl) |
| — | `sets` gana `code`, `released_at`, `set_type` (necesario para Scryfall) |
| — | DTO de respuesta propio para `User` (sin `hashed_password`) |
| — | Conservar el código y la arquitectura; rehacer solo los cimientos |

## 5. Modelo entidad-relación

```
users 1──N decks
formats 1──N decks
formats 1──N card_legality N──1 cards
sets 1──N cards
cards 1──N card_faces
cards 1──N card_rulings (por oracle_id)
cards 1──N card_deck N──1 decks
cards N──N tags (card_tag)
cards N──N cards (card_relationships)
```

## 7. Reglas de validación

### 7.1 Java (`DeckValidationService`)

- `validateCardAddition(deckId, cardId, quantity, section)`:
  - mazo y formato existen; sección válida; carta existe;
  - legalidad `banned` / `not_legal` → error;
  - `restricted` → máximo 1 en total;
  - límite de copias por formato (`max_copies`, `singleton`);
  - básicas y `unlimited_copies` exentas del límite de copias;
  - sideboard y main dentro de máximos;
  - reglas de companion.
- `validateDeck(deckId)`:
  - tamaño mínimo;
  - comandante requerido y válido;
  - identidad de color;
  - legalidad de todas las cartas;
  - devuelve **lista estructurada de errores**, no solo un booleano.

### 7.2 Trigger SQL (`check_card_quantity`)

`BEFORE INSERT OR UPDATE` en `card_deck`:

1. `quantity > 0` y `section` válida (además del `CHECK`).
2. Lee `format_id` del mazo y las reglas del formato.
3. Lee `legality_status` de `card_legality`.
4. Rechaza `banned` y `not_legal`.
5. Calcula copias **sumando todas las secciones** del mazo (no solo la actual).
6. Aplica `1` si `restricted` o `singleton`; si no, `max_copies`.
7. Exime básicas (`is_basic_land`) y `unlimited_copies`.
8. Valida `max_sideboard_size` y `max_deck_size` (si no son `NULL`).
9. Actualiza `decks.updated_at`.

El trigger es la red de seguridad; los mensajes amigables los da el servicio.

## 9. Estrategia de migración

1. Borrar `src/main/resources/scripts/01-create-schema*.sql` del runtime.
2. Sustituir `V2`–`V5` por un único `V1__baseline_schema.sql`.
3. Añadir `V2__seed_formats.sql` con Standard, Commander, Modern, Legacy,
   Vintage y Pauper. Draft y Brawl quedan fuera: un futuro modo draft usará su
   propia lógica de Limited y no requiere un formato jugable predefinido.
4. Dejar `V3__add_card_embeddings.sql` para cuando se elija modelo y dimensión.
5. Recrear la BD local (`docker compose down -v && up -d db`).
6. Reescribir `FlywayMigrationSmokeIntegrationTest` para validar `V1` + seed.
7. Documentar que, a partir de aquí, las migraciones son inmutables.

## 11. Criterios de aceptación

- [ ] `V1` crea el esquema completo en una BD vacía.
- [ ] `V2` siembra los formatos y sus reglas.
- [ ] Flyway es el único mecanismo de creación de esquema.
- [ ] Las entidades arrancan sin errores contra el esquema real.
- [ ] El trigger rechaza baneadas, restringidas y exceso de copias.
- [ ] El servicio rechaza mazos por debajo del mínimo y comandantes inválidos.
- [ ] `deck_contents` se persiste y se recupera sin pérdidas.
- [ ] `hashed_password` no aparece en ninguna respuesta.
- [ ] El test de drift recorre todas las tablas.
